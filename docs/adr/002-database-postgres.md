# ADR 002: Використання PostgreSQL як основного сховища даних

* **Статус:** Прийнято (Accepted)
* **Дата:** 2026-11-17

## Контекст
Проєкт передбачає зберігання даних користувачів, списків покупок, окремих товарів, категорій, а також складних зв'язків між ними (наприклад, управління правами доступу — хто з користувачів має права на перегляд чи редагування конкретного спільного списку). Дані мають чітку структуру, а консистентність списків (щоб товари не губилися і не дублювалися) є критично важливою.

## Рішення
В якості основної бази даних ми обираємо реляційну СУБД **PostgreSQL**.

## Наслідки

### Позитивні (Pros):
* **ACID-транзакції:** PostgreSQL гарантує надійність транзакцій, що унеможливлює пошкодження даних під час одночасного редагування списку кількома користувачами.
* **Зв'язки:** Реляційна модель ідеально описує структуру: `Користувачі <-> Списки <-> Товари`.
* **DevOps-friendly:** PostgreSQL легко розгортається в контейнерах (Docker) для локального середовища розробки, а також підтримується у вигляді керованих сервісів (Managed RDS) у всіх провідних хмарних провайдерах.
* **JSONB:** Можливість зберігати напівструктуровані дані у форматі JSONB, якщо нам знадобиться зберігати гнучкі налаштування користувачів без зміни схеми БД.

### Негативні / Компроміси (Trade-offs):
* **Масштабування на запис (Write-scaling):** На відміну від NoSQL-рішень (наприклад, MongoDB чи Cassandra), реляційні БД складніше масштабувати горизонтально. При значному зростанні кількості користувачів нам доведеться налаштовувати реплікацію (Master-Slave) та направляти всі операції читання на репліки, що ускладнить архітектуру.
