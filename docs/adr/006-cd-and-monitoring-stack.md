# ADR-006: Впровадження безперервного розгортання (CD) та стеку моніторингу

* **Статус:** Прийнято (Accepted)
* **Дата:** 23.11.2026
* **Контекст:** Лабораторна робота №5 (Автоматизація розгортання та спостережуваність)

## Контекст та проблема
Після успішного налаштування інфраструктури у хмарі Azure за допомогою Terraform та автоматизації конфігурації середовища через Ansible (ADR-005), оновлення застосунку вимагало ручного підключення по SSH до віртуальної машини та перезапуску контейнерів. Окрім того, у системі були відсутні інструменти для централізованого збору метрик апаратних ресурсів (CPU, RAM, мережа) та оперативного сповіщення про критичні стани інфраструктури.

## Розглянуті варіанти
1. **Ручний деплой та базові утиліти CLI (`htop`, `docker stats`):** не масштабується, схильний до людських помилок, не зберігає історію метрик та не підтримує автоматичні сповіщення.
2. **Хмарні SaaS-рішення (Datadog, New Relic):** надають потужний функціонал із коробки, але є платними та надлишковими для поточного масштабу проєкту.
3. **GitHub Actions (SSH CD) + Prometheus + Grafana + Exporters:** безкоштовний, індустріально стандартний стек із відкритим вихідним кодом, який легко інтегрується в існуючий `docker-compose.yml` без змін коду самого застосунку.

## Прийняте рішення
1. **Безперервне розгортання (CD):**
   * Розширено пайплайн `.github/workflows/ci.yml` етапом `deploy`, який запускається автоматично після успішної збірки та публікації Docker-образів (`build_and_publish`).
   * Використано `appleboy/ssh-action` для безпечного підключення до Azure ВМ за допомогою секретів репозиторію (`SERVER_HOST`, `SERVER_USER`, `SERVER_SSH_KEY`), оновлення коду, завантаження актуальних образів із `ghcr.io` та перезапуску сервісів.
   * Додано післядеплойний **Smoke Test**, який перевіряє доступність веб-інтерфейсу за HTTP-статусом `200 OK`.

2. **Стек спостережуваності (Observability) та алертинг:**
   * Розгорнуто систему збору метрик **Prometheus** (інтервал опитування `15s`) разом із агентами **Node Exporter** (метрики хост-системи) та **cAdvisor** (метрики Docker-контейнерів).
   * Налаштовано візуалізацію у **Grafana** (порт `3001`) із використанням перевірених дашбордів спільноти (ID `1860` для Node Exporter та ID `14282` для cAdvisor).
   * Реалізовано правило сповіщення (**Alert Rule**) `High Memory Usage` на базі PromQL-запиту, яке переводить алерт у стан `Firing`, якщо використання оперативної пам'яті перевищує `90%`.

### 1. Автоматизований CI/CD пайплайн та Smoke Test
Успішне проходження всіх етапів пайплайна (`quality_and_security` $\rightarrow$ `build_and_publish` $\rightarrow$ `deploy`) у GitHub Actions із підтвердженням доступності сервісу (`HTTP 200`):

## Наслідки (Consequences)
* **Позитивні:**
  * Повністю виключено ручне втручання при доставці нових версій коду на продакшн-сервер.
  * Забезпечено повну прозорість споживання ресурсів як на рівні віртуальної машини, так і на рівні окремих мікросервісів.
  * Система автоматично фіксує критичне навантаження на ресурси та сигналізує про потенційні збої.
* **Негативні / Компроміси:**
  * Запуск 4 додаткових контейнерів моніторингу збільшив базове споживання оперативної пам'яті на інстансі `Standard_B2ts_v2` (1 GiB RAM) до ~95%, що потребує ретельного контролю лімітів ресурсів.
  * Виникла необхідність відкриття додаткового вхідного порту `3001` у Network Security Group (NSG) Azure для доступу до веб-інтерфейсу Grafana.
